# Tai-e 软件分析平台：从数据流到指针分析

> **技术栈**：Java 17 · Tai-e 静态分析框架 · 数据流分析 · 指针分析 · 污点分析
> **代码仓库**：`NJU-Software-Analysis-Tai-e-assignments`（基于 [Tai-e](https://github.com/pascal-lab/Tai-e) 教学框架）

---

## 1. 项目概述

Tai-e 是一个用 Java 写的静态分析框架，提供 IR、控制流图、过程间控制流图、调用图、堆模型和分析调度。这个项目是它的八个课程作业：从一条**数据流方程**，做到**上下文敏感指针分析**，最后在指针分析之上写一个**污点分析**客户端。

八个作业不是并列的八个小程序，而是一条链：

```
A1 活跃变量 ──┐
A2 常量传播 ──┴─→ A3 死代码检测
A2 常量传播 ──→ A4 过程间常量传播 ──→ A7 别名感知常量传播
A4 调用图（CHA）──→ A5 指针分析 ──→ A6 上下文敏感指针分析 ──→ A8 污点分析
```

后面的作业直接复用前面的结果，越往后越接近"真实的静态分析工具"。

## 3. 软件分析技术

### 3.1 数据流分析：三个要素

每个分析都在回答三个问题：

| 要素 | A1 活跃变量 | A2 常量传播 |
| --- | --- | --- |
| **格**（值域 + 偏序） | 变量集合，子集包含 | 三值格，UNDEF < 常量 < NAC |
| **传递函数** | `IN = use ∪ (OUT − def)` | 按语句求值，kill + gen |
| **方向与边界** | 后向，`OUT[exit] = ∅` | 前向，入口参数为 NAC |

不变的是骨架：初始化 → 沿边 meet → 传递 → 直到不动点。变的是格和函数。

### 3.2 两个"死"

A3 把"死代码"拆成两个独立来源：

- **控制流不可达**：常量传播算出条件恒真/恒假，不可行的分支不再遍历；
- **数据流不可达**：活跃变量说明左值没人读、右值无副作用，赋值可以删。

这两类判断都建立在"前序分析已经算出的事实"上，而不是重新推理。这也是静态分析工具常见的组织方式：底层分析产事实，上层分析做决策。

### 3.3 过程间分析：把方法边界变成边

A4 的技术点在于：过程间分析没有新公式，只有**新的传递函数位置**。

| 边 | 规则 |
| --- | --- |
| `CallEdge` | 实参 → 形参 |
| `CallToReturnEdge` | 杀掉调用点左值 |
| `ReturnEdge` | 多个 return 值 meet → 调用点左值 |

节点上还是 A2 的过程内规则，只是"事实要跨方法流动"。这个抽象一旦建立，后面指针分析的跨过程传播用的是同一种思路。

### 3.4 调用图：从 CHA 到指针分析

- **CHA** 只看声明类型和类层次：可靠（不漏调用）、不精确（多算调用）；
- **指针分析** 看变量实际指向哪些对象：精确，但要先解出指向关系。

A5、A6 做的就是这件事。它和普通数据流分析最大的差别是：**图是分析过程中长出来的**。只有发现了新对象，才能为"这个对象上的字段"建边；图不全，结果就不可靠。

### 3.5 指针分析的两个集合

任何指针分析都围绕两样东西：

1. **指向集**：每个指针（变量、静态字段、实例字段、数组元素）可能指向哪些对象；
2. **指针流图**：指向关系往哪里流。

求解就是反复做"合并指向集 → 把新增部分推给后继 → 触发新规则"。`delta`（新增对象）是整个算法的性能核心：只处理真正变了的对象。

### 3.6 上下文敏感：精度是怎么买来的

A6 把方法、变量、对象都按上下文拆开，同一个方法可以在多个上下文里各分析一次。三种 k=1 选择器的区别：

| 选择器 | 记住的是 | 精度 | 规模 |
| --- | --- | --- | --- |
| 1-call | 哪个调用点 | 高 | 大 |
| 1-obj | 哪个接收对象 | 高（区分同类的不同实例） | 大 |
| 1-type | 哪种分配类型 | 中 | 小 |

k=2 版本用"最近一层 + 当前元素"的截断方式控制上下文长度，否则上下文会无限增长。

这是静态分析里最典型的一组取舍：**没有免费的精度**。

### 3.7 分析客户端：污点分析

A8 是典型的客户端分析：不自己重新做指针分析，而是**在指针分析上打补丁**。

- source：把特定对象标记为污点，并记住来源调用点；
- transfer：在源指针与目标指针之间加污点流边；
- sink：分析结束后检查实参的指向集里有没有污点。

污点沿第二张图（TFG）传播，同时并入 `delta`，让字段、数组、调用规则继续为它建边。这种"主分析 + 插件规则"的结构，正是工业界漏洞扫描工具的组织方式。

## 4. Java 能力

框架本身就是一份高质量的 Java 代码，作业要求"融进框架"而不是"另起一套"，所以这里用到的不是语法糖，而是能支撑扩展的语言特性。

| 特性 | 用在哪 | 作用 |
| --- | --- | --- |
| **泛型** | `AbstractDataflowAnalysis<Stmt, SetFact<Var>>`、`InterSolver<Method, Node, Fact>` | 一套求解器服务多种格，算法与数据类型解耦 |
| **接口 + 多实现** | `ContextSelector` 六个实现 | 换敏感度只需换一个类，求解器不动 |
| **访问者模式** | `StmtVisitor<Void>` 处理语句 | 新语句类型的规则集中在一处，不用长 if-else |
| **非静态内部类** | `StmtProcessor` | 直接访问求解器状态，避免层层传参 |
| **`instanceof` 模式匹配** | `stmt instanceof StoreField sf` | 判断与绑定一次完成 |
| **switch 表达式** | 运算符分派 `case ADD -> ...` | 无 fall-through，分支必须返回值 |
| **枚举** | `CallKind`、`Edge.Kind`、各 `Op` | 穷尽检查，拼写错误编译期暴露 |
| **不可变对象** | `ListContext` | 上下文可安全缓存、可作 map key |
| **`Optional`** | `stmt.getDef()` | 显式表达"可能没有" |
| **函数式集合 API** | `stream().map().toList()`、`forEach` | 把遍历与转换写成声明式 |
| **`ArrayDeque`** | 工作列表、闭包遍历 | 明确队列/栈语义，常数开销小 |
| **工厂方法** | `PointsToSetFactory.make()` | 屏蔽创建细节，限制直接 new |
| **模板方法** | `initialize()` 钩子 | 一次性预计算放在正确的时机 |

## 5. 工程能力

### 5.1 只改该改的地方

每个作业都只替换框架留出的抽象方法或类，不改框架内部。好处是显而易见的：框架升级不影响作业，作业之间还能互相复用。

### 5.2 复用是逐层搭起来的

| 复用关系 | 具体表现 |
| --- | --- |
| A2 被 A4 复用 | 过程间分析直接 `new ConstantPropagation(...)`，不复制求值逻辑 |
| A4 的求解器骨架被 A7 复用 | 只加两个入口，不做第二套 ICFG 遍历 |
| A5 被 A6 复用 | 主循环、`propagate`、`processCall` 结构不变，只换指针类型 |
| A6 被 A7、A8 复用 | 指针分析结果作为输入，不用重新解指向关系 |

### 5.3 增量而不是重算

三处都在做"只处理变化"：

- A2 工作列表只在前驱事实变化时传播；
- A5 用 `delta` 只处理新对象，避免重复建边；
- A7 在 store 改变值时主动唤醒依赖它的 load。

### 5.4 保守性写在显式规则里

静态分析的正确性靠"宁可多算，不可漏算"。这些判断都被写成了独立的、可检查的函数：

- A3 的 `hasNoSideEffect`：new / cast / 字段 / 数组 / 除法都算有副作用；
- A2 的除零判断：返回 `UNDEF` 而不是某个常量；
- A7 的下标匹配：只有"常量相等"或"一侧不确定"才算可能命中。

### 5.5 自我修正

- A5 的 `addPFGEdge` 为了判断源指针有没有指向集，线性扫描了全图；A6 直接改成读源指针的指向集；
- A7 的别名集合用两两遍历算出，复杂度高，报告中明确记录了这个瓶颈和可能的优化方向；
- A3 保留了一个未使用的辅助方法和一行调试输出，属于收尾没清干净。

写分析最容易犯的错不是算错，而是"实现能跑但不知道代价在哪"。把这些地方标出来，比假装没有问题更有用。
